# The grain stays an SVG turbulence filter

_2026-09-21_

The dashboard's paper texture is built in [`ux/theme/palette.mjs`](../../ux/theme/palette.mjs)
by `grain()`, as an inline `<svg>` running `feTurbulence`, tinted to the ink and
tiled at 140px. **Do not bake it into a bitmap.** It was tried and reverted on
the owner's explicit instruction.

## What was tried

The field was pre-rendered at build time into a 140×140 indexed PNG — a
a grain module under `ux/theme/` — deleted, so do not go looking for it — which
generated the noise, quantised it to sixteen alpha levels
and deflated it into a `data:` URI, which `ux/scripts/generate-theme.mjs` then wrote
into the stylesheet once per mode.

The reasoning was sound and the bug it addressed is real: `feTurbulence` is
_procedural_ noise, generated by the browser every time it paints that surface
rather than copied from a tile it already holds. That costs nothing on a surface
painted once and scrolled as a unit by the compositor, and it is not free on the
one element in this app that holds still while everything moves — the harness
panel's `position: sticky` section heading, which has to be re-drawn in a new
place on every frame and was re-running the filter to do it. When that misses the
frame the heading composites at the previous frame's position: it falls behind
the scroll and catches up, which reads as the heading not keeping up with the
page.

## Why it was reverted

**It changed what the paper looks like, which was never on the table.** A PNG is
a fixed grid of pixels stretched across 140 CSS px, so on a 2x display every
speck is painted at twice its intended size. The tooth stops being tooth and
becomes visible mottling. An SVG filter is rasterised at the device's own
resolution, and that is the entire reason the speckle disappears into the surface
instead of sitting on top of it — it is not an implementation detail of the
texture, it _is_ the texture.

It also cost bytes, which was known and accepted at the time and is worth
recording anyway: noise is the one thing that does not compress, and
`ux/app/theme.generated.css` went from 9.2kB to roughly 30kB.

## It happened again the same day

Predicted above, and it still happened. A later session on 2026-09-21 audited the
harness animations for performance, found `feTurbulence` on the `position: sticky`
section heading, correctly identified it as the most expensive thing in the view,
and re-applied the bitmap — reasoning its way to exactly the same fix, and being
right about the performance and wrong about the app. Reverted again on the
owner's instruction.

Two things made it easy to walk into. The audit was framed as "is the animation
optimized", which is a question about frames and not about paper. And a backup of
the deleted `grain.mjs` was still sitting in the session's scratchpad, so
restoring it was one `cp`. If you are reading this with a copy of that file in
front of you, that is not evidence it should go back.

## What was tried instead, and was also wrong

`ux/app/globals.css` promoted the pinned heading to its own compositor layer:

```css
.harness-panel .view-section > .section-head { will-change: transform; }
```

The heading went on lagging, and on 2026-09-21 the owner said so again. It was
removed. Two things were wrong with it, and both are worth keeping.

**The grain is not a filter, it is an image.** `--grain` is a `url()` data URI
holding an SVG — the engine decodes and rasterises that 140px tile once per size
and device scale and then blits it like any other background image. A CSS
`filter: url(#…)` is the thing that re-runs on every paint; a background image is
not, however it was drawn. So the per-frame cost the promotion was buying its way
out of was mostly not there. **Everything above about baking a bitmap still
stands** — that was always a question about what the paper looks like, and it is
still answered no.

**It was the wrong element.** Corrected later the same day, after the layer tree
was finally read: the lag was never about this band's paint at all. The bands were
each on a compositor layer while the box that scrolls them had none, so the prose
moved on the main thread and the bands were placed separately, a frame apart. The
hint belongs on the scroller. The full account, the measurement and the CDP recipe
are in
[`a-lagging-pinned-band-is-the-scroller.md`](a-lagging-pinned-band-is-the-scroller.md).

Two things to carry away. Promoting the band does not fix this — twice tried,
twice useless — so if you are reaching for `will-change` on a heading, you are on
the wrong element. And removing it does not fix it either: for a while this note
claimed the promotion *caused* the lag, which was a guess that survived one
session and was wrong. Profile before changing anything.

None of which touches the bitmap question. That is about what the paper looks
like, and it is still answered no.

Regenerate with `npm run gen:theme` after any change to `palette.mjs`; the
generated stylesheet is committed.
