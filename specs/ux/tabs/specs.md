# Specs [SPC]

The binding specification for the view over the specs themselves: every binding design, readable without leaving the surface, and never changed from it.

> 🔒 **An agent may not edit this file.** The prohibition extends to any alteration of it, rewording, reformatting, renaming and moving included, and admits no exception for a change the agent judges harmless. Where an agent finds anything wrong, inconsistent or improvable, it records the finding in [`REVIEW.md`](../../REVIEW.md) with its reasoning and leaves the entry for a person to clear, never treating its own entry as settled. Until a person applies a change, this file is complied with as written; where it and the repository diverge, the repository is wrong.

---

## Purpose and Scope

| #   | Provision | What it means |
| --- | --- | --- |
| 1   | **This specification is the single source of truth for how the specs are read back.** | The specs decide what the system must be, and until they had a view they were read only by opening files in an editor. This file states what that view must hold. The reading rules, the binding rule and the approval gate in [`README.md`](../../README.md) apply to it unchanged. |
| 2   | **It governs a reading of the specs, never the specs themselves.** | What a spec may say, and how one is written, is the business of [`README.md`](../../README.md). What waits to be applied is the review view's. |
| 3   | **It binds where it speaks and defers where it is silent.** | Compliance is mandatory: an agent chooses how to satisfy a row, never whether to. Silence confers no authority to invent a requirement and attribute it here. |

## Specifications Register

> ⚠️ **When referencing:** always cite a row by **both** its ID and its spec statement — IDs shift, specs get removed, and ordering isn't guaranteed.

| ID | SPEC STATEMENT | SPEC RATIONALE | DESIGN RECOMMENDATION |
| --- | --- | --- | --- |
| **SPC-001** | The view presents the specs in their own order and names them by their own names. | The specs are cited by path and ID, so a view that regroups or renames them breaks every citation the moment someone follows one. A reader who cannot map the page onto the folder holds two structures and acts on the wrong one. The test: the entries on this view, in order and by name, match the specs folder on disk. | Render each folder as it sits on disk — folders first, then files, alphabetically — with a sentence against each entry and nothing regrouped or renamed. The one departure is that a README and `ARCHITECTURE.md` sort to the top of their group, because they exist to be read first. Falls short in that the departure is a choice the folder itself does not make, so a new file meant to be read first sorts wherever its name puts it. |
| **SPC-002** | This view cannot render a byte of the record, at any depth, by any path. | It takes a path from the address bar, and the folder it reads sits beside the one holding everything personal. A traversal here is her journal on a page about the specs, reached by editing a URL. The test: any path resolving outside the specs folder is refused — by climbing, by absolute form, and by any encoding of either. | Resolve every path through one function that rejects anything landing outside `specs/`, and give the view no other way to read a file. It works because the check sits where the path becomes a file, so no route can skip it. Falls short in that it guards this view's reads only; a link on a spec page that points into `data/` still navigates, to a page gated like any other. |
| **SPC-003** | Each entry carries a sentence saying what it governs. | A spec file's name says its area, not what it binds — `purpose.md` and `privacy.md` sit side by side and neither name says which one decides what may leave the surface. The sentence is what lets a reader pick the right file without opening them all. The test: every entry on this view has a description, and none is its own name restated. | Use the file's line from the specs index where it has one, and fall back to its lede, the one sentence every spec file opens with. It works because both are written by whoever wrote the spec, so the view invents nothing. Falls short in that a file missing from the index and missing a lede gets no sentence, and the view shows the gap rather than filling it. |
| **SPC-004** | Nothing on this view changes a spec. | The specs change only when a person has read the exact words and applied them, with a commit saying why. A control here — a toggle, an inline edit, an accept button — would turn that into a click nobody can trace. The test: no control on this view or below it writes to a file. | Render every entry as content, with no control that has an effect, and link a spec to its pending drafts in the review queue rather than offering to apply them. It works because the absence is total, so there is no state in which a control appears. Falls short in that it makes only this view read-only; the files themselves are protected elsewhere, or not at all. |
| **SPC-005** | A spec is reached from the view by the same path it has on disk. | Specs are pointed at by path in commits, findings and code comments, and each of those pointers should open the file it names. An address scheme of the view's own would break them at exactly the moment someone follows one. The test: the address of every file on this view contains its path below the specs folder, and the page header states it. | Address each file as `/specs/` followed by its path below `specs/`, and show that path in the header as segments, each opening its folder. It works because the address and the disk cannot disagree. Falls short in that a spec cited by ID alone, with no path, still has to be found by hand. |
| **SPC-006** | If the specs cannot be read, the view says what that means rather than reporting an empty folder. | A missing specs folder means the surface is running against a checkout with no binding design in it, and a reader shown "nothing here" will conclude there are no rules and move on. The test: with the folder absent, the view says the specs are missing and what follows from that; with it present and empty, it says that instead. | Tell the two apart at the read and write a notice for each, the missing one stating the consequence: nothing on the surface can then say what the system is meant to be. It works because the cause is known where the folder is read. Falls short in that a folder present but half-emptied reads as a smaller set of specs, not as a loss. |

> 📚 **No row above carries a source tag, and that is a value rather than an omission.** These registers govern one person's private record; where no published work genuinely addresses a row it stays bare, and reaching for a large name to decorate one is the failure mode — see **Source tags** in [`README.md`](../../README.md). The works cited elsewhere in these specs, and the boundary past which each stops applying, are in [`REFERENCES.md`](../../REFERENCES.md).
