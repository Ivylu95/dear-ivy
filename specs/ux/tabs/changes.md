# Changes [CHG]

The binding specification for the view over the repository's own history: every commit, what a row may say about one, and the one thing it must never show.

> 🔒 **An agent may not edit this file.** The prohibition extends to any alteration of it, rewording, reformatting, renaming and moving included, and admits no exception for a change the agent judges harmless. Where an agent finds anything wrong, inconsistent or improvable, it records the finding in [`REVIEW.md`](../../REVIEW.md) with its reasoning and leaves the entry for a person to clear, never treating its own entry as settled. Until a person applies a change, this file is complied with as written; where it and the repository diverge, the repository is wrong.

## Purpose and Scope

| #   | Provision                                                    | What it means                                                                                                                                                                                                                                                                                     |
| --- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **This specification is the single source of truth for what the surface may show of the repository's history.** | The harness is amendable one traceable change at a time; nothing said where that trace becomes legible, or what it may contain when it does. This file does. The reading rules, the binding rule and the approval gate in [`README.md`](../../README.md) apply unchanged.                              |
| 2   | **It governs a reading of history, never a client for it.** | This is not an editor, not a general repository browser and never a diff. Whether the surface may write at all is [`purpose.md`](../purpose.md) (`DSH-001`); what a commit message may contain is architectural and is not restated here.                                                              |
| 3   | **It binds where it speaks and defers where it is silent.** | Compliance is mandatory: an agent chooses how to satisfy a row, never whether to. Silence confers no authority to invent a requirement and attribute it here — in particular, silence about a form of content is not permission to render it.                                                          |

## Specifications Register

> ⚠️ **When referencing:** always cite a row by **both** its ID and its spec statement — IDs shift, specs get removed, and ordering isn't guaranteed.

| ID | SPEC STATEMENT | SPEC RATIONALE | DESIGN RECOMMENDATION |
| --- | --- | --- | --- |
| **CHG-001** | The view shows what changed and never what the change said. | A difference over the personal half of the repository is her journal rendered on a page about the machine, and it is the one blurring of the two halves this surface cannot have. The failure is quiet: the feature would be built for the harness, work correctly, and expose the record as a side effect on the first commit that touched both. The test: nothing on this view renders a line of file content, from either half. | Ask the version control system for messages, paths and line counts only, and never for content. It works because the restriction is at the boundary where content would enter rather than at the point it would render, so no view downstream can reintroduce it. The handoff is the full identifier at the foot of an opened row: where the message is not enough, the reader has everything needed to look elsewhere. |
| **CHG-002** | A row says which half of the repository it touched. | The repository holds two things that move independently — a record being written and the rules being amended — and a commit touching both is a rule change that rewrote something already written, which is the one kind worth noticing on sight. Without the marking, the list is an undifferentiated stream in which that case is invisible. The test: every row is attributable to one half, the other, or both, without opening it. | Classify by the paths a commit touched and mark the row accordingly. It works because the classification comes from the same data the row already carries, so it cannot disagree with the paths shown when the row is opened. Its limit: a classification by path is only as good as the layout, and a personal byte written outside its folder would be marked wrong — which is a boundary failure rather than a view one. |
| **CHG-003** | The view says whether the current state of the record is saved. | Everything else on the page is about the past; this is the only question here whose wrong answer costs something, because a session runs on a machine that may be reclaimed without warning and anything written but not pushed dies with it. A history view that shows forty saved commits while something unsaved sits on disk is showing the reassuring half of the truth. The test: the unsaved state is visible before any historical row is read. | Render the working state first, above the log, from its own read. It works because two independent reads mean neither queues behind the other and a slow log cannot delay the one time-sensitive fact on the page. Its limit: it reports what the checkout says, which is nothing about whether the remote accepted a push. |
| **CHG-004** | The absence of a repository is reported as an ordinary condition, not as a fault. | A deployment with no working tree is the normal shape of a hosted build — it ships files rather than a repository — and drawing that as an error teaches the reader to ignore the treatment that means something is actually wrong. A genuine failure to read a repository that *is* present is a different condition and must look different. The test: the two states are distinguishable on sight, and the ordinary one says where the history can be read instead. | Distinguish the two at the read and give each its own notice, with only the genuine failure drawn as one. It works because the distinction is made where the cause is known rather than inferred from an empty result. Its limit: it does not cover a repository that is present, readable, and empty, which is its own stated state. |
| **CHG-005** | The list shows a bounded number of rows and offers more without losing the reader's place. | Every row carries its message and its paths into the page whether or not anyone opens it, and the whole history of a repository is a payload nobody asked for — most of it behind a control nobody clicked. But the alternative that renders detail on demand cannot work without scripts, and a history that cannot be read with scripts off is the worse trade. The test: extending the list leaves the rows already on screen where they were. | Show a page of rows and offer a plain link that doubles the count, leaving the scroll position alone. It works because the list is read from the top and what a reader wants is more of it below what they are looking at, not the same amount somewhere else. Its limit: doubling has no upper bound stated here, so a large enough repository reintroduces the payload problem. |
| **CHG-006** | A narrowing that matched nothing is distinguished from a history with nothing in it. | These are two different pages that look the same, and the second is alarming in a way the first is not. A reader who has filtered and sees an empty page concludes the repository is empty, or that something is broken — and neither is recoverable from without knowing how they got there. The test: each of the two states says which it is, and the narrowed one offers the way back. | State the active narrowing and what it is showing out of, and write the empty case to say the filter matched nothing and what the filter actually searches. It works because the message names the likely mistake — searching a filename where only messages are read — rather than reporting emptiness. Its limit: it presumes the narrowing is visible, which is the same row's first requirement. |

> 📚 **No row above carries a source tag, and that is a value rather than an omission.** These registers govern one person's private record; where no published work genuinely addresses a row it stays bare, and reaching for a large name to decorate one is the failure mode — see **Source tags** in [`README.md`](../../README.md). The works cited elsewhere in these specs, and the boundary past which each stops applying, are in [`REFERENCES.md`](../../REFERENCES.md).

## Unwritten

- Whether a path under the personal half may be shown in full on an opened row, given that a filename can itself be personal.
- Whether the view has an upper bound on what it will render, and what it does at it.
- Whether history from before a restructuring is reachable, and how a reader is told the shape changed.
