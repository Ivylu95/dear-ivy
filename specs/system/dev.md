# Development [DEV]

The binding specification for the developer's experience: what working on this system is like for the person who builds it, while agents do the work.

> 🔒 **An agent may not edit this file.** The prohibition extends to any alteration of it, rewording, reformatting, renaming and moving included, and admits no exception for a change the agent judges harmless. Where an agent finds anything wrong, inconsistent or improvable, it records the finding in [`REVIEW.md`](../REVIEW.md) with its reasoning and leaves the entry for a person to clear, never treating its own entry as settled. Until a person applies a change, this file is complied with as written; where it and the repository diverge, the repository is wrong.

---

## Purpose and Scope

The provisions below fix this specification's purpose and the reach of its authority — how this file is to be read, obeyed, and bounded. The register further down governs the developer's experience instead.

| # | Provision | What it means |
| --- | --- | --- |
| 1 | **This specification is the single source of truth for the developer's experience.** | Code shows what agents did and the history shows what changed; neither says what working alongside them should be like for the developer. This file states it, so the developer knows what to expect and an agent knows what it owes them. The reading rules, the binding rule and the approval gate in [`README.md`](../README.md) apply unchanged. |
| 2 | **It binds in development sessions only, and governs the developer's experience, never how an agent makes a change.** | DEV-001 decides when these rows are in force: a session switched into development mode. How an agent makes a change to the harness is not this file's; its rows are drafted separately. Where things live is [`ARCHITECTURE.md`](ARCHITECTURE.md)'s, and what the human interface layer may do is [`../ux/`](../ux/)'s. Where two appear to bind the same question, the more specific governs, and the overlap is raised rather than settled quietly. |
| 3 | **This specification binds where it speaks, and silence is not permission.** | Compliance is mandatory: an agent chooses how to satisfy a row, never whether to. Anything the developer is asked to do that no row anticipated is a gap raised before it is asked. |

## Specifications Register

The normative part of this file. Each row is one thing that must be true of the developer's experience; how a row is read is in [`README.md`](../README.md).

> ⚠️ **When referencing:** always cite a row by **both** its ID and its spec statement — IDs shift, specs get removed, and ordering isn't guaranteed.

| ID | SPEC STATEMENT | SPEC RATIONALE | DESIGN RECOMMENDATION |
| --- | --- | --- | --- |
| **DEV-001** | A session follows development practice only when the developer has switched it on. | Everyday sessions and the developer's share one harness. Commit discipline and review queues are noise in an everyday conversation, and they cost context on every turn they are loaded. An explicit switch keeps each session to one audience. Compliance is judged by whether a session nobody switched loads none of these rows, and a switched one loads all of them. | A `/dev-mode` command loads this register and the agent-practice rows for the rest of the session, and says so in its first reply; without it nothing here loads, and CTX-001 keeps it out of the always-loaded layer. Falls short in that the switch lasts one session: a developer who forgets it gets the everyday defaults, which is the safe way round. |
| **DEV-002** | Every decision is put to the developer one at a time. | A batch of decisions is approved as a batch: the reader skims the fourth after judging the first, and a wording nobody weighed lands with the rest. One at a time, each gets the attention it needs, and a no costs nothing else. Compliance is judged by whether any reply asks the developer to decide more than one thing. | Put one row, one question or one choice in each reply, handed over whole, and wait for the answer before the next. Everything else pending is listed, not asked. Falls short when decisions depend on each other, like a row and the provision it needs, which are put together and said to be one decision. |
| **DEV-003** | Everything waiting on the developer is in one place. | A request made in passing is lost in passing: an action asked for in one reply and not again is found weeks later, or never, and nothing says it was waiting. One list makes the developer's share of the work visible at a glance. Compliance is judged by whether every open request to the developer can be found from that list alone. | Keep a single list of what waits on the developer — commands to run by hand, rows to paste, decisions pending — at the head of the review queue. Add to it in the same change that creates the wait, and clear an item when it is done. Falls short when two sessions add at once and word the same item twice. |
| **DEV-004** | The developer never has to referee two agents. | Two sessions working one tree can each be right and still collide: one builds what the other undoes, a commit carries the other's unsaved work, and the developer is left to work out which was meant. The clash is paid for in the developer's attention, the scarcest thing in the system. Compliance is judged by whether a clash between sessions reaches the developer as one question, never as a mess to untangle. | Before writing a file another session has open, message that session. Commit only your own lines, and where two sessions have built rival things, stop both and put the choice to the developer once. Falls short where a session cannot be reached: its work is then left untouched and named in the list of what waits on the developer. |
| **DEV-005** | A step left to the developer comes with the exact command and why no agent took it. | A step handed over vaguely is a second task: the developer has to work out what to run, and whether an agent simply gave up. Knowing the reason is also how a wrong refusal gets noticed and fixed. Compliance is judged by whether each step left to the developer can be done by copying what was given. | Give the command in a copyable block with the directory it runs from, quote the rule that stopped the agent, and add the step to the list of what waits on the developer. Never route around the rule to spare the developer the step. Falls short for a step with no single command, which is given as a checklist instead. |
| **DEV-006** | A new term enters the system's vocabulary only once the developer confirms it. | A word used once may be a passing phrase or a deliberate rename, and the two need opposite handling. Adopted unasked, a passing phrase spreads through the harness as a rename nobody chose; ignored, a real rename has to be asked for twice. One question settles which. Compliance is judged by whether every term adopted can be traced to the developer saying yes. | When the developer uses a new name for something, ask once whether to use it from now on and whether it belongs in the defined terms, and keep the existing term until they answer. Put it as its own decision, after the one in hand, so it never rides along with another. Falls short when the developer is mid-flow, where the question waits in the list of what waits on the developer rather than interrupting. |
| **DEV-007** | The developer can see what every agent changed, and why, without reading files. | Agents change the harness faster than anyone reads diffs, and several at once. A change the developer cannot see is a change they cannot question, and a harness that moves unseen stops being theirs to steer. Compliance is judged by whether the developer can say, from one screen, what changed today and the reason for each change. | Show every commit on the Changes view of the human interface layer with its reason, and have each session name, at the end of its reply, every commit it pushed. Falls short for work not yet committed, which is visible only in the session doing it. |
| **DEV-008** | The human interface layer serves the developer's work as well as everyday use. | Most of what the developer is asked to do — judge a drafted row, find what waits on them, see what an agent changed — happens today in a chat and in files, which ties it to a desk and a terminal. The layer already shows the harness, the review queue and the changes, so it is the one surface that can hold all of it. Compliance is judged by whether everything the developer is asked to judge or do can be found from the layer. | Give the developer's views — the review queue, the list of what waits on the developer, the Changes view and the harness — their own section, apart from everyday use, and build them to the same standard as the rest. Falls short where DSH-001 holds: the layer shows a step to run by hand but cannot run it, so it gives the exact command instead. |
| **DEV-009** | The developer learns what needs fixing without seeing the record. | The developer is not a member of the record's repository, so the findings that once showed what landed badly now sit where the developer cannot look. A harness that never hears about its failures stops improving for the one person it serves. Compliance is judged by whether a finding raised in the person's session is ready for the developer, with nothing personal in it and nothing asked of the person. | Write each finding about the harness in non-personal terms to one file of its own in the person's repository; when the person asks whether there is anything for the developer, answer with it, for the person to forward. The developer reproduces each against the fabricated record. Falls short in that it reaches the developer only when someone asks, and in that the non-personal test is the agent's judgement — the reason nothing leaves on its own (the approved SFG row, *"Nothing personal leaves the machine in a request the agent makes."*). |

> 📚 **No row above carries a source tag, and that is a value rather than an omission.** These registers govern one person's private record; where no published work genuinely addresses a row it stays bare, and reaching for a large name to decorate one is the failure mode — see **Source tags** in [`README.md`](../README.md). The works cited elsewhere in these specs, and the boundary past which each stops applying, are in [`REFERENCES.md`](../REFERENCES.md).
